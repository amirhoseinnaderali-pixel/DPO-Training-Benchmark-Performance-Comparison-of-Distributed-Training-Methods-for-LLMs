# DPO Distributed-Training Benchmark

A controlled benchmark of distributed training strategies for **Direct Preference Optimization (DPO)** under a fixed two-GPU workload.

> **Research status:** the original notebook contains historical single-run measurements. The controlled benchmark introduced in this branch has **not yet been executed**, so no new performance ranking is claimed.

## Research question

> Under the same DPO workload, how does the distributed training strategy affect throughput, training time, GPU memory usage, and DPO training behavior on a fixed 2-GPU system?

### Broader research context

This project is part of a larger research direction around **efficient adaptation and reasoning under compute constraints**. Here the focus is deliberately narrower: isolating training-system choices before studying how adaptation and reasoning interact.

## Experimental design

The controlled study fixes:

- TinyLlama/TinyLlama-1.1B-Chat-v1.0
- Anthropic HH-RLHF
- deterministic 90/10 train/evaluation split
- seed = 42
- LoRA r=16, alpha=32
- DPO beta = 0.1
- max length = 512
- max prompt length = 256
- learning rate = 5e-7
- one training epoch
- fp16
- effective global batch size = 16
- two processes / two GPUs

The primary comparison is:

1. DDP
2. FSDP
3. DeepSpeed ZeRO-2
4. DeepSpeed ZeRO-3

The old single-process Standard run is preserved as **historical evidence**, not mixed into the primary controlled comparison.

CPU offload is not silently bundled into the primary strategy comparison. Offload should be studied as a separate factor.

## Metrics

Each run records:

- synchronized train-loop time
- Trainer-reported runtime
- examples/sec
- optimizer steps/sec
- peak allocated GPU memory per rank
- peak reserved GPU memory per rank
- host RSS
- final training loss
- DPO reward accuracy
- DPO reward margin
- hardware/software environment
- git SHA
- configuration hash

## Historical result

The original notebook ran each configuration once. Those measurements are retained for provenance in:

- `RESEARCH_AUDIT.md`
- `results/historical/original_notebook_results.json`

The historical results showed:

| Method | Historical wall time (s) | Historical table throughput |
|---|---:|---:|
| Standard | 336.79 | 2.67 samples/s |
| FSDP | 517.47 | 1.74 samples/s |
| ZeRO-2 | 242.60 | 3.71 samples/s |
| ZeRO-2 Optimized | 208.76 | 4.31 samples/s |
| ZeRO-3 | 1097.17 | 0.82 samples/s |

These numbers are **not presented as a definitive ranking** because the original configurations were confounded and each was run only once.

## Run

Install the dependencies in a clean environment.

First run the smoke test:

```bash
python scripts/smoke_test.py
```

Run one method:

```python scripts/run_benchmark.py --method ddp```

Run the full controlled comparison:

```python scripts/run_benchmark.py```

Generate a summary from raw results:

```bash
python scripts/analyze.py
```

> Full execution requires a compatible multi-GPU CUDA environment. The repository does not claim that the benchmark has been reproduced until raw result JSON files are generated by an actual run.

## Limitations

This benchmark answers a narrow systems question on a specific model, dataset, hardware setup, and DPO/LoRA regime. It does not establish which distributed strategy is universally better, nor does it measure large-scale full-parameter LLM training.

The historical run also had unresolved environment and timing issues. See `RESEARCH_AUDIT.md`.

## Next experiment

The immediate next step is to execute the controlled benchmark with repeated runs. Only after those measurements exist should the repository make quantitative claims about the relative trade-offs between methods.
